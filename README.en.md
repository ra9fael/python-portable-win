# Portable Python Workspace

A fully isolated, self-bootstrapping, zero-pollution portable Python environment for Windows: **copy the whole folder to any path on any machine and keep developing and running**. No dependency on the host Python, and nothing is written to `%APPDATA%`.

## Mental Model

- **One directory = one interpreter + a flat `site-packages`.** No virtualenv.
- **The entry point is `python.exe` itself**: activate the shell, or point your IDE at `python/python.exe`.
- **The only things that break on relocation are artifacts with a recorded absolute path** — launchers generated by pip/uv. `repair.py` replaces them automatically; you do not need to handle it manually.

## Core Features

- **100% isolated:** strict environment variables; no pollution from or to the host machine.
- **Self-bootstrapping:** one script installs a full Python engine (python-build-standalone via `uv` when available, otherwise the official embeddable package).
- **No `.bat` entry points:** the interpreter is the entry point; package launchers become path-relative shims that repair themselves after a move.
- **Automatic re-shelling:** launchers are checked and repaired after install, on activation, and on any interpreter start.
- **Seamless IDE integration:** standard `site-packages` plus a `${workspaceFolder}` config that survives relocation.
- **Lossless upgrades:** dependencies are exported before an engine upgrade and can be restored afterwards.
- **Optional distribution template:** `App.exe` demonstrates shipping an app on top of this environment; it is not required for development.

## Quick Start

### 1. Initialize

```powershell
.\scripts\bootstrap.ps1
```

When `uv` is on `PATH`, python-build-standalone is installed (full stdlib, bundled Tcl/Tk, no `._pth` patching) and the PEP 668 marker is removed. Otherwise the official embeddable package is used. Force either mode with `-Engine pbs` / `-Engine embeddable`; the default is Python 3.14.7 (`-Version` to change). An existing environment triggers an offer to export `requirements.txt` first.

Downloads are verified against `scripts/checksums.psd1`; a mismatch aborts and keeps the old environment. Override with `-PythonSha256` / `-GetPipSha256`, or use `-SkipChecksum`. To move to a new patch release or another architecture, refresh hashes first with `.\scripts\update_checksums.ps1 -Version <x.y.z> -Arch amd64,arm64,win32`. For restricted networks, `-Mirror <engine mirror prefix>` (passed to `uv --mirror` for PBS, used as the download prefix for embeddable) and `-PipIndexUrl` (exported as `PIP_INDEX_URL` / `UV_INDEX_URL`) are available. Add `-NonInteractive` for CI or unattended runs.

### 2. Install Dependencies

```powershell
.\scripts\pip.ps1 install numpy pandas jupyterlab
```

With `uv` available this runs `uv pip ... --system` (faster, cache stays inside the package); otherwise it falls back to `python -m pip`. Every install immediately rewrites the generated `.exe` files as path-relative shims and restores the project's `sitecustomize.py` if a package replaced it. `--user` is rejected.

For reproducible restores, generate a hash-pinned lock file:

```powershell
.\scripts\pip.ps1 lock     # requirements.in / requirements.txt / pyproject.toml -> requirements.lock
```

`bootstrap.ps1` prefers `requirements.lock` when restoring dependencies and falls back to `requirements.txt`.

### 3. Activate and Run

```powershell
. .\scripts\activate.ps1
python -m jupyter lab      # or python main.py / pytest / ruff
```

Activation sets `PYTHONNOUSERSITE`, puts `python/` and `python/Scripts/` on `PATH`, points Tcl/Tk at the bundled runtime, keeps pip/uv caches and `JUPYTER_DATA_DIR` inside the package, and repairs stale launchers if the package was moved. `deactivate` restores everything.

> Prefer `python -m <tool>` over calling `Scripts\<tool>.exe` directly — it bypasses the launcher layer entirely.

### 4. Optional: run through `App.exe`

```powershell
.\scripts\bootstrap.ps1 -WithLauncher
.\App.exe
```

The ~10 KB launcher reads `app.ini`, resolves `python\python.exe` relative to itself, sets the environment, and starts the configured module. It is a sample of shipping an app on this environment, not a development requirement.

## How It Works (Summary)

`python.exe` derives `sys.prefix` from its own location, so the interpreter and `site-packages` are inherently relocatable. Only **launchers** break: pip/uv append the absolute interpreter path to each `.exe`.

This project replaces those launchers with `scripts/bin/shim.exe` (~7 KB, contains no paths). Identity lives in a sibling `<name>.entry` text file, and the shim derives the interpreter from its own location at runtime. Repair does not require a launcher: `pip.ps1` runs it after install, `activate.ps1` on activation, and `sitecustomize.py` on interpreter start and exit.

After activation, `uv pip install` is pinned to the in-package interpreter through `UV_*` variables; `sitecustomize.py` also appends the package `Scripts` directory to child-process `PATH` and pins `PIP_USER` / `PIP_CACHE_DIR`, so tools that call `pip.exe` cannot install into the user profile.

Full details, launcher comparison, and limits: [Architecture](docs/en/architecture.md). There is also an interactive [HTML tutorial](tutorial/portable-python-tutorial.en.html) (English; switch to Chinese in the page).

## Shared Runtime (Consumer Mode)

For a new project, generate the scaffold from a clone of this repository:

```powershell
git clone https://github.com/ra9fael/python-portable-win.git C:\tools\python-portable-win
C:\tools\python-portable-win\scripts\new-portable-project.ps1 `
  -ProjectRoot D:\dev\github\my-app `
  -AppDir app `
  -Requirements requirements.txt `
  -PythonVersion 3.12.10
```

It adds and pins the `vendor/python-portable-win` submodule, generates `scripts/build-portable.ps1`, and adds `.portable/` to `.gitignore`. Then:

```powershell
cd D:\dev\github\my-app
# Adjust the stage/TODO section in scripts/build-portable.ps1
.\scripts\build-portable.ps1
```

If the project already has the submodule:

```powershell
.\vendor\python-portable-win\scripts\new-portable-project.ps1 -ProjectRoot . -AppDir app -Requirements requirements.txt
```

The scaffold supports three profiles:

| Profile | Use case | Output |
|---|---|---|
| `app` (default) | Single application | submodule + `scripts/build-portable.ps1` + `.portable/` |
| `scripts` | Personal portable script workspace | a copied `scripts/` tree, no submodule, code in `my_tools/` |
| `multi` | Several apps in one repository | submodule + one `scripts/build-<app>.ps1` per app + `build-all.ps1` |

```powershell
# Personal scripts: scripts/ is a checked-in copy, no submodule
.\scripts\new-portable-project.ps1 -Profile scripts -ProjectRoot D:\dev\my-tools -AppDir my_tools

# Multiple apps: each app gets its own <app>/.portable
.\scripts\new-portable-project.ps1 -Profile multi -ProjectRoot D:\dev\my-suite `
  -AppDirs apps/one,apps/two
```

For `multi`, `-Workspace` is relative to each app (default `.portable`); the generated `build-all.ps1` builds every app in sequence.

Manual equivalent:

```powershell
git submodule add https://github.com/ra9fael/python-portable-win.git vendor/python-portable-win
New-Item -ItemType Directory .portable

.\vendor\python-portable-win\scripts\bootstrap.ps1 -Workspace .\.portable -Engine embeddable -Version 3.12.10
.\vendor\python-portable-win\scripts\pip.ps1 -Workspace .\.portable install -r requirements.txt
.\vendor\python-portable-win\scripts\build_release.ps1 -Workspace .\.portable
```

Conventions:

- `.portable/` is generated output; add it to the project `.gitignore`. Do not point `-Workspace` at the repository root, or runtime `scripts/` will mix with your own scripts.
- `-Workspace` puts `python/`, `scripts/repair.py`, `scripts/sitecustomize.py`, `scripts/bin/shim.exe`, and `dist/` inside that directory.
- Pin the Python version with `-Version`. For a project-local checksum table:

```powershell
.\vendor\python-portable-win\scripts\update_checksums.ps1 `
  -Workspace .\.portable -ChecksumFile .\.portable\checksums.psd1 -Version 3.12.10
.\vendor\python-portable-win\scripts\bootstrap.ps1 `
  -Workspace .\.portable -Engine embeddable -Version 3.12.10 `
  -ChecksumFile .\.portable\checksums.psd1
```

- Upgrade by bumping the submodule commit and rebuilding. Without `-Workspace`, the default behaviour is unchanged.
- Project-specific native DLLs (for example `msvcp140.dll`) stay in the project build script and are copied into `.portable\python\`; do not add them to the upstream repository.
- Compiled artifacts (Cython `.pyd`, Nuitka output, and similar) belong to the application build layer, not this repository. Stage them into `<workspace>/app` and they ship as-is; this repository does not compile or encrypt anything. The Python used for compilation must match the bundled engine's minor version and architecture. The embeddable engine does not ship headers, so compile with the same CPython version in your development environment and verify `import` inside the package. Never ship the `.py` source for a protected module alongside its `.pyd`.

## Shipping an App

1. Create an app directory (e.g. `my_app/`) with `main.py`.
2. Configure `app.ini` if you want the launcher:

```ini
[app]
module = my_app.main
gui = false
# app_dir = my_app   # optional extra PYTHONPATH entry
```

3. Run it with `python -m my_app.main`, or double-click `App.exe` once built.

`gui = true` launches through `pythonw.exe` (no console window). One-off overrides:

```powershell
.\App.exe --module my_app.gui
.\App.exe --script my_app\main.py -- --verbose
```

### Build a Release

```powershell
.\scripts\build_release.ps1                                        # auto-named from folder + Python version + arch
.\scripts\build_release.ps1 -ReleaseName "MyApp_v2"                # MyApp_v2.zip
.\scripts\build_release.ps1 -ReleaseName "MyApp" -AppendDateTime   # MyApp_20260520_1430.zip
.\scripts\build_release.ps1 -Wheelhouse                            # include an offline wheels/
```

`-Wheelhouse` downloads every installed dependency (with its dependency tree) into `wheels/` and packages it. On an offline machine, `sitecustomize` points `PIP_FIND_LINKS` at that directory, so `python -m pip install --no-index <package>` works.

The packager:

1. Streams `python/`, `scripts/`, `app.ini`, `.vscode/`, app dirs (and `App.exe` when present) directly into the ZIP — no staging copy.
2. Detects launchers by content and replaces them with `shim.exe` + `<name>.entry`; real compiled binaries (e.g. `ruff`) are kept as-is.
3. Rewrites extensionless-script shebangs (e.g. `numba`, `jsonpointer`).
4. Excludes caches (`__pycache__`, `.pip_cache`, `.uv_cache`, `.portable_root`); `wheels/` is omitted unless `-Wheelhouse` is used.

## Upgrading Python

Do not delete or replace `python/` manually:

1. Edit `$Version` in `scripts\bootstrap.ps1`, or pass `.\scripts\bootstrap.ps1 -Version "3.13.7"`.
2. Run the script. It offers to export `requirements.txt`, replaces the engine, then offers to restore the packages.

The exact installed patch version is written to `python/.portable_version`; a later run without `-Version` reuses it, so floating requests such as `3.14` do not drift over time.

## Adding Tkinter

The PBS engine ships Tcl/Tk; the embeddable engine does not:

```powershell
.\scripts\add_tkinter.ps1
```

Downloads are verified against `scripts/checksums.psd1`; override with `-Sha256`, skip with `-SkipChecksum`, or use `-Mirror`. If Tcl/Tk is already present (PBS or a previous run), the script exits without changes; add `-Force` to reinstall. `activate.ps1` sets `TCL_LIBRARY`/`TK_LIBRARY`; `sitecustomize` and `App.exe` also set them when the shell was not activated.

Select `python/python.exe` as the interpreter in VS Code or PyCharm. The bundled `.vscode/settings.json` uses `${workspaceFolder}`, so completion, linting, and debugging keep working after the workspace moves.
